# Local-Jev v1: a Jev-compatible decision server on small local models

Status: ready-for-agent

Read `GLOSSARY.md` and ADR-0001 to ADR-0003 in `docs/adr/` first; this spec uses their vocabulary and does not restate their reasoning.

## Problem Statement

The developer received a technical proposal (a first draft generated by a search engine's AI overview) claiming that a 1.7B model plus xgrammar-constrained JSON could reach "leading metrics" on jevbench. Research showed most of its premises were wrong: "JEV" is not "JSON Evaluation", jevbench does not use the proposal's four-field schema or measure TTFT, vLLM cannot load LFM3 yet, and grammar-constrained JSON is not how strong entrants produce probabilities.

The developer still wants to know, with numbers, whether a small model (≤ 3B parameters) hosted locally can act as a credible Jev-compatible system: accurate enough, well calibrated, fast enough, and usable on Traditional Chinese as well as English States. They also want the result packaged so it runs the same way on their Apple Silicon Mac (with OrbStack) and later on a Linux NVIDIA GPU host they do not have yet, with Python managed by uv.

## Solution

A small HTTP server that speaks the TypeSafe `/v1/systemone` wire format, so jevbench's built-in `typesafe` adapter can evaluate it unchanged. Each server process runs exactly one Decider, chosen at startup:

- **LFM3 Option-ID Decider**: `LiquidAI/LFM3-1.7B` (a Chat model) answers through Option-ID scoring, which yields Native probabilities from a single forward pass with thinking disabled. It can optionally write a Reason.
- **d1 Decider**: `LiquidAI/d1-2B` (a Decision model) answers natively through its own `system_one` head, also in one pass.

Both Deciders share per-Question-type temperature calibration fitted on jevbench's public Tasks. A single CLI serves a Decider, runs jevbench against it (English public Tasks plus a Traditional-Chinese copy), fits calibration, and produces a comparison report. The developer gets a feasibility report in Traditional Chinese with a clear verdict, plus a Dockerfile, compose files and a dev container that run the same code on CPU, with CUDA on a GPU host and natively on MPS on the Mac.

## User Stories

### Answering Questions

1. As the developer, I want the server to accept a `/v1/systemone` request containing a State and named Questions, so that jevbench's `typesafe` adapter can talk to it without modification.
2. As the developer, I want a `noul` Question answered with P(yes) as a number between 0 and 1, so that jevbench reads it as a yes/no Distribution.
3. As the developer, I want a `choice` Question answered with the most likely Label and a Distribution over exactly its Label set, so that jevbench accepts the answer as valid.
4. As the developer, I want a `score` Question answered with a Distribution keyed by level index, so that jevbench can score ordinal answers.
5. As the developer, I want every answer to carry its Question type, so that jevbench's type check passes.
6. As the developer, I want every Distribution to sum to 1 by construction, so that no answer is ever rejected for bad arithmetic.
7. As the developer, I want a request with several named Questions answered under the same names, so that the server honours the full wire format, not just jevbench's single `decision` Question.
8. As the developer, I want State given as plain text or as JSON, so that structured States work the same way jevbench sends them.
9. As the developer, I want Criteria shown to the model for every Label (or level), so that the Decision uses the Question's own definitions.
10. As the developer, I want `choice` Questions with up to 26 options supported, so that Label sets larger than jevbench's current maximum of 6 still work.
11. As the developer, I want `score` Questions with 2 to 10 levels supported, so that the server matches what d1 supports.
12. As the developer, I want a clear 4xx error for unsupported Question types (`text`, `number`, `date`, `box`, `boxes`, multi-select `choice`) and for malformed requests, so that misuse fails loudly instead of returning nonsense.
13. As the developer, I want the response to include token usage, so that jevbench's cost accounting has something to record.
14. As the developer, I want the response to include the server's own timing for the request, so that the report can separate model time from network and client overhead.

### Deciders

## Implementation Decisions

### Modules

- **Wire API**: validates `/v1/systemone` requests, dispatches each named Question to the active Decider, builds responses, exposes the health endpoint and optional bearer auth. Requests are handled one at a time (single worker, serialised model access).
- **Decider interface** (ADR-0003): takes a State and a Question, returns a Decision (raw Distribution plus any extras such as a Reason). The highest seam in the system; the Wire API depends only on it.
- **LFM3 Option-ID Decider**: renders the prompt through the model's chat template with thinking disabled, maps Labels to Option IDs, asks the backend for next-token probabilities over those IDs, normalises over the Label set, maps back to Labels. Optional Reason generation through the backend.
- **LM backend interface** (ADR-0001): two capabilities only, next-token probabilities over a given set of candidate tokens after a prompt, and plain bounded text generation. v1 implementation on Hugging Face transformers.
- **d1 Decider**: wraps the d1 model's `system_one` call, converts the wire Question into d1's question format, converts d1's answer back (adding the Question type, keying `score` probabilities by level index, using `noul` as P(yes)).
- **Calibration**: applies per-Question-type temperature scaling to a raw Distribution (scale log-probabilities by 1/T, renormalise). Loaded per Decider; identity when absent. Temperature scaling never changes the argmax, so Accuracy is unaffected; only calibration metrics move.
- **Calibration fitter**: reads raw per-Task Distributions and expected Labels from a benchmark run, fits T per Question type by minimising negative log-likelihood, reports k-fold (k=5) cross-validated Brier and ECE, writes the calibration for that Decider.
- **Bench runner**: fetches jevbench at the pinned commit into a cache, runs it with the `typesafe` adapter against a given server for the selected Task sets, then summarises and merges runs into the comparison report.
- **zh-TW Tasks**: a committed, derived copy of the 231 public Tasks with only the State translated, plus its integrity check.
- **CLI**: one entry point with subcommands to serve (with a Decider choice, host, port), run the benchmark, and fit calibration.

### API contract (TypeSafe `/v1/systemone`, as jevbench's `typesafe` adapter uses it)

Request (`POST`, optional `Authorization: Bearer …`):

```json
{"state": "…text or JSON…", "model": "…", "explain": false,
 "questions": {"decision": {"type": "choice", "instructions": "…",
                            "criteria": {"track_order": "…", "cancel_order": "…"}}}}
```

- `noul` criteria are keyed `"true"`/`"false"`; jevbench's Labels for it are `yes`/`no`.
- `score` criteria are a list of level descriptions, lowest first; Labels are the level indices as strings (`"0"`, `"1"`, …).
- `explain` is our extension (default false). `model` is echoed back; it does not select anything.

Response (200):

```json
{"answers": {"decision": {"type": "choice", "choice": "track_order",
                          "probabilities": {"track_order": 0.91, "cancel_order": 0.09},
                          "reason": "…only when explain is true and the Decider supports it…"}},
 "usage": {"input_tokens": 0, "output_tokens": 0}, "model": "…", "timing": {…}}
```

- `noul` answers: `{"type": "noul", "noul": <P(yes)>}`.
- `score` answers: `{"type": "score", "score": <argmax level>, "probabilities": {"0": …, "1": …}}`.
- jevbench's acceptance rules (from its `typesafe` adapter at the pinned commit): `answers.decision` must exist; its `type` must equal the Question type; `noul` must be a non-boolean number in [0, 1]; `choice` must be one of the Labels and `probabilities` must be a dict; `score` must have a `probabilities` dict. Extra fields are ignored.

### Decider details

- **LFM3**: `LiquidAI/LFM3-1.7B`, revision pinned (see Further Notes), `trust_remote_code`, chat template options `enable_thinking=False` (renders an empty think block). ChatML with BOS `<|startoftext|>`; EOS `<|im_end|>`. Read the next-token distribution at the start of the assistant's answer, restricted to the Option IDs. The implementer verifies that every Option ID is a single token in the exact position used; if a letter is not, adjust the prompt framing, not the maths. The card's sampling defaults (temperature 0.1, repetition_penalty 1.1) apply only to Reason generation, never to scoring.
- **d1**: `LiquidAI/d1-2B`, revision pinned, loaded with `AutoModel` and `trust_remote_code`; needs `transformers>=5.19` plus `torchvision` and `pillow`. Not a Chat model: no chat template, no generation, no Reason. Native answer fields per its card: `noul`; `choice`, `confidence`, `probabilities`; `score`, `confidence`, `probabilities`, `legend`. The implementer verifies the real field names and `score` key format against the live model in the real-model tier.
- Both Deciders: bf16 on CUDA and MPS, fp32 on CPU, overridable.

### Packaging

- uv project named `local-jev`, package `local_jev`, Python 3.12, lockfile committed. Runtime dependencies: torch, transformers (≥ 5.19), torchvision, pillow, huggingface_hub, FastAPI, uvicorn, pydantic. Dev dependencies: pytest, ruff, httpx. No xgrammar, no vLLM (ADR-0001, ADR-0002).
- torch comes from the PyTorch CUDA 12.8 index on linux/x86_64 via uv sources with platform markers, and from the default index elsewhere (CPU on linux/aarch64, MPS-capable on macOS). `uv sync` and `uv lock` cannot use `--torch-backend`; use explicit indexes and markers.
- Dockerfile: multi-stage, `ubuntu:24.04` base, uv binary copied from a pinned `ghcr.io/astral-sh/uv` image, uv-managed Python 3.12, `dev` and `runtime` targets, non-root user, gcc kept in the runtime image because Triton compiles kernels at run time (LFM3's conv kernel uses Triton on CUDA). No `nvidia/cuda` base: torch wheels bring their CUDA libraries; the host needs the NVIDIA driver and the NVIDIA container toolkit.
- Compose: one service per Decider, both behind profiles so only the selected one starts (the two together need about 15 GB in fp32, at OrbStack's 15.7 GiB limit). Shared named volume for the Hugging Face cache; model id and revision via environment; health check on the health endpoint. A GPU override file adds NVIDIA device reservations; it is delivered unverified (no GPU host exists yet).
- Dev container: built from the `dev` target, GPU optional (used when the host has one), shares the Hugging Face cache volume, runs `uv sync` on create. Must work with OrbStack. On the Mac it runs on CPU; MPS is only available natively.
- Native Mac use: the serve subcommand via `uv run` picks MPS automatically.

### Benchmark mechanics (jevbench at the pinned commit)

- Run with `python -m jevbench.cli run --tasks <file> --adapter typesafe --endpoint <server base URL> --model <name> --key-env TYPESAFE_API_KEY --results <new file> --raw-dir <new dir> --ledger <file>` then `python -m jevbench.cli summarize --tasks … --results … --public-export <file>`.
- The `typesafe` adapter refuses to run if the key environment variable is empty: set a dummy value when the server has no token.
- Its cost reservation needs prices or an explicit reserve for unknown endpoints: pass zero prices or a reserve (the implementer confirms which flag the CLI accepts).
- Results must go to new files outside jevbench's own checkout; there are no retries, and HTTP 401, 403 or 429 stops a run.
- jevbench itself uses only the standard library; it is cloned, not installed as a dependency.

## Testing Decisions

- A good test drives external behaviour through a seam and asserts on what a caller sees (the response, the fitted calibration, the report), never on prompt strings, internal call order or private helpers.
- **Main seam: the `/v1/systemone` HTTP contract**, exercised in-process. Fakes are injected only at the model boundary: a fake LM backend returning fixed next-token logits for the Option-ID Decider, and a fake d1 model returning canned `system_one` answers. Covers request validation, all three Question types, Option-ID mapping and normalisation, calibration application, `explain`/Reason behaviour for both Deciders, error responses, and conformance with jevbench's acceptance rules listed above. ADR-0001's backend seam and ADR-0003's Decider seam are injection points, not separate test suites.
- **Second seam: the calibration fitter** (raw results in, temperatures and cross-validated report out), plus the zh-TW Task integrity check.
- **Real-model tier** (pytest marker `real_model`, excluded by default, run on demand): the main seam with the real LFM3-1.7B and d1-2B, and an end-to-end smoke test that runs jevbench's own `typesafe` adapter on 10 Tasks against a real server. This tier is the only one that can catch remote-code incompatibilities, multi-token Option IDs, or d1 field drift.
- Prior art: none in this repo (greenfield). jevbench's `typesafe` adapter is the reference for what a valid answer is.
- Build test-first at these seams (the `tdd` skill), fast tiers on every change, the real-model tier before merging and after any model, revision or transformers change.

## Out of Scope

- vLLM (until it supports LFM3), SGLang, llama.cpp backends; batching; multiple workers.
- xgrammar and any grammar-constrained decoding; a Verbalized-probabilities baseline; Label scoring (ADR-0002).
- Fine-tuning or LoRA; comparison models beyond the two Deciders (the configuration must still allow swapping models).
- TTFT and tokens-per-second metrics (jevbench does not use them).
- d1's other Question types (`text`, `number`, `date`, `box`, `boxes`), multi-select `choice`, pictures, video and audio.
- A Reason for the d1 Decider (no pairing with a Chat model).
- Submitting to jevbench's official board (that needs a maintainer-run request on hidden Tasks).
- Verifying the GPU path on real hardware; production hardening beyond optional bearer auth.

### Feasibility verdict criteria (agreed)

On the 231 public Tasks, zero-shot plus calibration, cross-validated figures. "Feasible, worth further investment" requires all of the following:

1. Valid answers 100% for every Decider.
2. The best Decider reaches Accuracy ≥ 80% and Brier ≤ 0.20.
3. Latency: record server-side p50 on the Mac with MPS. Server-side p50 ≤ 150 ms on an L4-class GPU stays "pending" until a GPU host exists.

The Traditional-Chinese copy is reported separately and does not affect the verdict.

Reference points from jevbench's results table:

| System | Accuracy | Brier | ECE | p50 |
|---|---|---|---|---|
| Jev 1.13.0 | 96.3% | 0.056 | 0.027 | 0.65 s |
| system-one-open (Gemma 4 E2B with LoRA, on an L4) | 90.1% | 0.138 | 0.068 | 0.65 s |

Liquid's card claims 77.9 on "JevBench v1.4.1" for d1-2B without naming the metric; treat it as unverified.

### jevbench scoring

- **Intelligence**: chance-corrected accuracy, using the argmax over the exact Label set.
- **Calibration**: ECE, Brier, TVD and RPS.
- **Speed**: `100 − 20·log10(s / 0.1 s)`, averaged over p50 and p95. Self-hosted latency is adjusted ×2, plus 0.15 s on maintainer-run servers.
- **Cost**.
- **Composite**: a weighted harmonic mean of the four axes with penalty gates. The open-weights board leads with Capability, the mean of Intelligence and Calibration.
- An invalid Distribution counts as wrong.
- Public Tasks: 231 in total.
  - easy: 36 choice, 12 noul.
  - original: 36 choice, 24 noul, 12 score.
  - hard: 67 choice, 38 noul, 6 score.
  - `choice` Label sets have 3 to 6 options.

### Original proposal, claim by claim (for the feasibility report)

| Proposal claim | Finding |
|---|---|
| JEV = "JSON Evaluation"; a fixed `is_applicable`/`category`/`confidence`/`reason` schema | Wrong. Jev is TypeSafe AI's decision model. jevbench asks typed Questions with per-Task Label sets and expects Distributions. |
| Optimise TTFT and tokens/s for jevbench | Wrong. jevbench measures whole-request wall-clock p50/p95, alongside accuracy, calibration and cost. |
| Model `LFM3-1.7B-Instruct` | The repo is `LiquidAI/LFM3-1.7B` (post-trained, no suffix). Custom code. Thinking is on by default. Context is 256K. |
| Serve with vLLM + xgrammar | No vLLM release supports LFM3. Support is in the unmerged vllm-project/vllm#64959; the newest release checked was v0.33.0rc3. |
| ChatML prompt template | Mostly right. It needs the BOS token and the empty think block, and the draft was missing an `<|im_end|>`. |
| Prefill `{` | Conflicts with a JSON-schema grammar, which would demand `{` again. |
| `reason` with `pattern` + `maxLength` | xgrammar drops the length bounds when `pattern` is combined with `minLength`/`maxLength`. vLLM's auto mode falls back to guidance. |
| `confidence` with `minimum`/`maximum` | Supported by xgrammar. |
| Keep the compiler cache warm | `GrammarCompiler` caches by default (`cache_limit_bytes`). |
| Temperature 0 for categoricals, 0.2 for the reason | Sampling parameters are per request; per-field temperature needs a custom logits processor. |
| Stop on `\n` or `}` | Redundant under a grammar, and `\n` can cut the JSON. |
| Context overflow mid-JSON | Not a real risk at 256K context. The real risk is `max_tokens` truncation, solved by bounded output. |

### Platform facts

- No container runtime on macOS (Docker Desktop, OrbStack, Podman, Lima) gives Linux containers Metal/MPS; OrbStack has no GPU support at all.
- vLLM on macOS is CPU-only and built from source.
- LFM Open License v1.0 does not license commercial use by entities with annual revenue of USD 10 million or more. This applies to both LFM3 and d1.
- The Mac has an M3 Pro with 36 GB. OrbStack limits containers to 15.7 GiB and 12 CPUs.

### Known risks

- LFM3 and d1 are about two weeks old. Their remote code may break on transformers changes, which is why revisions are pinned.
- Letter-position bias of a 1.7B model under Option-ID scoring.
- There is no public zero-shot baseline for a 1.7B model on jevbench.
- The GPU path is unverified.
- CPU inference in containers takes seconds per Decision. It is fine for development but not representative of latency.

The feasibility report and the README are written in Traditional Chinese, with technical terms kept in English. Code, comments, ADRs, the glossary and this spec are in English.
